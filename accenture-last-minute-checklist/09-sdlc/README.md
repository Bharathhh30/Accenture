# SDLC — Software Development Life Cycle

**Assessment priority: Role-dependent** — revise if the role/JD mentions software engineering, testing, Agile, or delivery; not a confirmed universal general MCQ section.

| Concept | One-line last-minute reminder |
|---|---|
| SDLC purpose | SDLC structures software work from needs discovery through delivery, operation, and maintenance. |
| Requirements | Requirements describe what stakeholders need and the constraints the system must satisfy. |
| Functional requirement | A functional requirement specifies system behavior or a capability. |
| Non-functional requirement | A non-functional requirement specifies a quality/constraint such as performance, security, availability, or usability. |
| Feasibility | Feasibility checks whether the project is viable technically, financially, operationally, legally, and on schedule. |
| Analysis and design | Analysis clarifies needs; design defines architecture, components, interfaces, and data structures. |
| Implementation | Implementation turns the design into code while following standards, reviews, and version-control practices. |
| Testing | Testing evaluates whether software meets requirements and behaves acceptably under expected and edge conditions. |
| Unit testing | Unit tests check a small isolated function/component. |
| Integration testing | Integration tests check interactions and data flow between combined components/services. |
| System testing | System testing evaluates the integrated product against system requirements. |
| Regression testing | Regression tests check that changes did not break previously working behavior. |
| User Acceptance Testing | UAT lets intended users/business owners validate that the system meets acceptance needs. |
| Verification vs validation | Verification asks whether the product is built according to specification; validation asks whether it meets user needs. |
| Waterfall | Waterfall uses sequential phases with heavier upfront planning and later phase handoffs. |
| Agile | Agile delivers in short feedback cycles, adapts priorities, and emphasizes working increments and collaboration. |
| Scrum | Scrum organizes work into timeboxed Sprints with defined accountabilities, events, and a prioritized Product Backlog. |
| User story | A user story expresses a capability from a user's perspective and is paired with acceptance criteria. |
| Acceptance criteria | Acceptance criteria define observable conditions that must be met for a story or feature to be accepted. |
| Product backlog | The Product Backlog is an ordered, evolving list of product work. |
| Sprint backlog | The Sprint Backlog is the selected Sprint work plus the plan to achieve the Sprint Goal. |
| Deployment | Deployment moves a tested release into a target environment using a controlled release process. |
| Maintenance | Maintenance fixes defects, adapts software to change, and improves performance/security after release. |
| Change management | Change management assesses, approves, records, and communicates changes to reduce operational risk. |
| Shift-left security | Shift-left integrates security and testing earlier in design/development rather than waiting until release. |
| SDLC and DevOps | DevOps adds continuous collaboration/automation across build, release, deployment, and operations rather than replacing lifecycle needs. |
